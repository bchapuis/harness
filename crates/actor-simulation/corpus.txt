# The fixed-seed regression corpus (spec §18.6, docs/simulation-testing.md).
#
# Every seed that ever failed belongs here. Once listed, it replays on every
# swarm run — local, CI, and soak alike — regardless of how wide that run's
# sweep is. That is what makes the suite a ratchet: a bug found once can never
# come back quietly, even in the edit loop where sweeps are only a few seeds.
#
# Format: one `<workload-name> <seed>` per line; `#` comments and blank lines
# ignored. The name is the workload's `name()` — the same string the failure
# reports, so a failure message names its own corpus key. A trailing comment
# after the seed is free-form; record what broke and where it was fixed.
#
# To add a seed, take it straight from the failure:
#
#     workload 'singleton-chaos/leader' failed at seed 900006
#     └─ becomes: singleton-chaos/leader 900006
#
# and replay it on its own with:
#
#     SWARM_SEED_BASE=900006 SWARM_SEEDS=1 cargo test -p <crate> --test <name>
#
# Corpus seeds are absolute: SWARM_SEED_BASE shifts a sweep, never these.

# --- Split-brain singleton after heal -----------------------------------------
#
# `2 live activations at quiescence on a healed, converged cluster`, against
# `singleton-converged-exactly-one` — plus, in leader mode, its mirror image,
# `0 live activations`. Recorded a hundred times over from collecting soaks
# (SWARM_CONTINUE=1) across the gossip, registry, and leader control planes at
# roughly 0.5-1% of seeds; `static`, whose membership never changes, was clean.
#
# Three separate reasons the workload asserted something it had not set up, none
# of them a defect in the singleton (utilities spec §4), which held its guarantee
# throughout — at most one activation per *converged* view:
#
#  1. The tail was never quiescent. `net.heal()` clears partitions but leaves the
#     wire's seeded frame loss running, so probes kept going missing, peers kept
#     flipping `suspect`/`unreachable`, and no two nodes' serving sets ever
#     agreed. A run could end mid-divergence however long it waited, and two
#     live activations across divergent views is exactly what §4 item 3 permits.
#     Fixed by `SimNetwork::quiesce()`, which the workload now calls with the
#     heal (`conformance_faults.rs::quiescing_the_network_stops_injecting_faults`).
#  2. The count lagged reality. A manager emits `SingletonStopped` when it
#     observes the termination, on its next tick, so an instance that stopped in
#     a run's last tick was gone while its `Stopped` was still 100ms away — and
#     counted as live. `SingletonConverged` now ends an activation at whichever
#     comes first, the manager's report or the actor's own `ResignId`.
#  3. Leader mode could dissolve the cluster. With `DowningPolicy::Timeout` each
#     isolated side downs the rest, `down` is terminal, and the fixed voter set
#     lets the survivors elect a leader that downs the previous one in turn —
#     ending with every node `Down`, no serving set anywhere, and correctly no
#     singleton at all. It now uses conservative downing, as its gossip twin
#     already did for the same reason.
#
# Pruned to a few seeds per mode, as the note here asked: they are one finding
# recorded a hundred times, and the durable guards are the three above.

# --- Remote register not linearizable under duplication -----------------------
#
# `no sequential order linearizes the N completed/pending operations` — a `Cas`
# that succeeded reported `false`. Around 0.2% of seeds, because it needs two
# faults at once: the request frame duplicated onto a mutating op, *and* the
# first reply dropped.
#
# The wire delivers both copies; the recipient handles both. The first `Cas`
# swaps the value and answers `true`, the second finds it already swapped and
# answers `false`, and with the first reply lost the caller resolves against the
# second. Both replies carry the same correlation id, so nothing downstream can
# tell them apart — there is no caller-side fix.
#
# That is the framework's contract, not a defect in it: at-most-once holds at the
# caller, and spec §7.2 puts exactly-once out of scope, "built atop this layer
# with explicit idempotency keys". The workload was the side claiming too much —
# a bare register is not a linearizable object over a duplicating wire. The
# register in `tests/support/` now carries that key on its mutating operations,
# which is the construction the spec prescribes, and the sweep is what shows it
# holds. `conformance_faults.rs`'s `duplication_is_tolerated_...` keeps asserting
# the double-handling underneath, and now says how the two fit together.
#
# Pruned to the two originals plus one from each later soak base.

linearizable-remote-register 10000125  # duplicated Cas applied twice; caller took the duplicate's reply
linearizable-remote-register 10000944  # same, found once the sweep stopped halting at 10000125

# --- Asks left pending at quiescence ------------------------------------------
#
# `[no-silent-loss] N ask(s) still pending at quiescence` — spec §18.5 #1 — and,
# where a dispatch was the thing still in flight, `[serial-execution] dispatch
# ... never completed`. Reproduced across four granary workloads and machine,
# which share only the actor framework and the cluster driver underneath. Three
# causes, found in that order, each one hiding the next:
#
#  1. The driver called quiescence too early. It flushed a fixed 2s after the
#     traffic finished — no longer than the deadline granary's own quorum append
#     carries, and that append fans out further asks behind it (the drained
#     stragglers of a committed quorum, §7.2). A call issued at the end of the
#     drive could not possibly have closed by the time the question was asked, so
#     a live call was reported as a lost one. `drive_cluster` now flushes and
#     then keeps advancing while any ask is in flight, capped, so a genuinely
#     abandoned one still reaches the invariant.
#  2. `try_join_all` abandoned asks for real. Granary fanned out blob puts, blob
#     gets, and spilled-value reads with `futures::future::try_join_all`, which
#     returns on the first error and drops the futures still in flight — with the
#     `ask`s they had already issued. Those never reach a reply or a `CallError`,
#     which is exactly what §18.5 #1 forbids. The four sites now use
#     `actor_core::join_all_results`, which awaits every future and then reports
#     the first error; the helper's doc is where the rule now lives.
#  3. Only then could the seeds behind these two run to the end, and two further
#     bugs surfaced — see the two sections below.
#
# Pruned to a couple of seeds per workload.

# --- Acknowledged write lost when two commands encode identically -------------
#
# `[grain-commit-monotonic] grain bank.Account/account/1 committed seq 2 not
# after previous head 2 (G3/G5)`. Unmasked by the fixes above; a genuine G14
# violation, and the most serious thing the corpus turned up.
#
# A replica refuses an append that lands on a slot it has already filled — the
# optimistic head check of granary §8, which is what stops a leader whose
# recovered head is stale from overwriting a committed record. It made an
# exception for a re-delivered append, and identified one *by its bytes*. But
# bytes are not an identity: this workload deposits one cent every time, so two
# clients' commands encode identically. A leader that recovered a stale head
# (its read quorum was not reached, so it fell back to its local view, §7.5)
# appended onto the occupied slot, every replica read it as a duplicate and
# stored it, and the append committed. Two clients were told their deposit was
# durable; the grain held one record.
#
# Fixed in `store.rs`: an append may proceed onto an occupied slot only if it is
# the same append — same shard term as well as same bytes — and the check now
# covers every slot of the batch, not just the first. Pinned by
# `store::tests::an_identical_record_from_a_newer_term_is_still_a_stale_head`.

granary-account-swarm 41000332

# --- Workspace read judged against an outcome the spec calls ambiguous --------
#
# `a read returned bytes other than the last committed write (F1/G14)`. Also
# unmasked by the fixes above, and a bug in the claim rather than the code.
#
# `granary-ws-swarm` recorded a path's expected content only on a successful
# `Put` and treated every failure as if nothing had happened. But `Unavailable`
# is ambiguous by definition (granary §7.2, §11): the record may already sit on a
# replica minority, and the next activation's quorum recovery can find it on a
# majority and adopt it — the spec's own fault list asks for exactly this case to
# be exercised. Reading those bytes back is correct. `GrainError::Unavailable`'s
# doc comment said the opposite ("so the write did not commit"), which is how the
# claim came to be written that way; both are fixed.

granary-ws-swarm 6

# --- A `Created` reply whose record is not in the journal on re-activation -----
#
# `p2 acknowledged Record(app.Session/keep-c1-2) — a name nothing in this run ever
# forgets — and a committed probe found it absent`. Around 1 seed in 1,500.
#
# UNRESOLVED. What the event stream shows on this seed, for one grain:
#
#   Committed seq=1
#   Record(keep-c1-1) -> Ok(Created)
#   Record(keep-c1-2) -> Ok(Created)     <- no Committed of its own
#   Rehydrated replayed=1                <- the journal holds one record
#   ...
#   probe Record(keep-c1-2) -> Created   <- committed probe: still absent
#
# Three mutating commands answered `Created` against two commits, and the next
# activation replayed two records. `GrainEvent::Committed` is emitted on the
# commit path *before* the reply is released (`host.rs`), so a `Created` with no
# preceding `Committed` is not an ordering artifact of the trace.
#
# The claim itself has been narrowed three times and each narrowing was a real
# test bug, so this one is recorded rather than asserted about granary:
#  - expectations were held on the workload, which a sweep shares across seeds
#    (that alone looked exactly like a G14 defect — see docs/simulation-testing.md,
#    "A workload outlives its runs");
#  - `Unchanged` was counted as an acknowledgement, though it commits nothing;
#  - the verification read was `List`, a query, which §7.5 serves from the
#    activation and explicitly does not make linearizable. It is now a *writing*
#    command, the construction §7.5 prescribes, so the answer is committed state.
#
# What is left is not explained by any of those. Reproduce with:
#
#     SWARM_SEED_BASE=9300730 SWARM_SEEDS=1 \
#       cargo test -p tenancy --test directory_swarm --exact \
#       the_directory_index_survives_the_cluster_swarm
#
# Disabling the churn traffic (keeping the entropy draw) makes this seed pass, but
# the same anomaly is still visible in its trace — a `Created` whose record is
# gone by the next activation — and merely self-heals there, because the client
# happens to record that name again. Churn decides whether the loss is observable,
# not whether it happens.

tenancy-directory-swarm 9300730
