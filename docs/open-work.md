# Open Work

**Status:** an index, not a specification. Nothing here is normative. Every entry points at the section that owns it, and that section is the source of truth — this page is a view over them, ordered by how much a reader has to know before the item makes sense. Nothing on this page blocks anything else on it, so the order is a reading order and not a dependency graph. A change of scope belongs in the owning spec first and here second.

**Each open item carries a next step**, so a session can pick one up cold. A next step is the first concrete move and what "done" looks like — file and symbol anchors, the ordering that matters, and the alternative if the first move turns out wrong. It is a starting point, not a commitment: the owning spec still decides scope, and a next step that proves misconceived should be rewritten here rather than followed. Items in §3 and §4 carry none on purpose, for the reason each section gives.

**Each item also carries a status**, because "unfinished" covers three situations that call for different moves, and a reader who cannot tell them apart will start the wrong one:

- **open** — nothing is built, or something was attempted and did not reach the property. The next step is the work.
- **postponed** — it could be built now and deliberately is not. The entry says what would change that, so the call is re-examined on new evidence rather than re-litigated from scratch.
- **by design** — the owning spec declined it (§3). No session changes this by writing code; the move is to change the spec's mind.

A **landed** item does not appear on this page at all. It is deleted from here and from its spec in the same commit, and git holds what happened — the specs describe the tree as it stands, not the road to it. The one thing that survives its own commit is a **decision**: where work was built and pulled back, or considered and declined, the entry records what was decided, when, and what would reopen it. That is the part git hides, and the part a later session would otherwise pay for twice.

The status is the first line under each heading, so `grep '^\*\*Status' docs/open-work.md` is the whole page at a glance. There is deliberately no summary table above: a second copy of these lines is a second thing to keep true, and this page has no drift test to keep it honest the way the registry and catalogue tables in the specs do.

The tree carries no TODO backlog. A sweep of `crates/` finds zero `todo!()`, zero `unimplemented!()`, zero `#[ignore]`, and zero `TODO`/`FIXME`/`HACK` comments; the only two marker hits in the repository are a vendored `clang-sys` artifact under `guest/qjs-runner/target/` and an `mktemp` template in `scripts/bench-machine-cost.sh`. That is a property worth keeping: unfinished work here is *declared in a spec*, where a reader can see its cost and its blast radius, rather than dropped as a comment beside the code that would have to change. The consequence is that "what is unfinished" cannot be answered by grepping the code, which is why this page exists and why grepping *it* has to answer instead.

## 1. Compatibility policy, mechanised but never exercised

Both checks that keep **V4**/**V5** from decaying into prose now exist (compatibility §4). The golden corpus: every registered boundary has checked-in bytes at its current revision, a test beside the format decodes them, and a completeness gate fails the build when a new boundary ships without them (`crates/compat/tests/golden_corpus.rs`, which reads the §3 registry out of the spec and holds the tree to it in both directions). And mixed-version simulation: negotiation pinned node by node, and a nemesis that walks a `Rollout` across releases.

The sidecars are done. The Raft term and snapshot pointers, granary's per-shard fences and seals, and the blob-store tombstones are stamped boundaries with checked-in bytes; each reader still adopts its unstamped predecessor, and each writer now emits the stamped form. Two of them were not in the spec's list: the fence and the seal, which were the most dangerous of the set, and which the list did not mention. What compatibility §5 still lists as unstamped is §1.2 through §1.4, in its priority order; each is a place where a format change today is a migration rather than an edit.

### 1.1 No boundary has a second revision

**Status:** postponed — the vocabulary and the sweeps exist; a revision to exercise them *with*, and the seams that would only matter once one did, deliberately do not. Reopens with the first real format change.

**What exists.** Negotiation is pinned node by node, and a swarm sweeps a `Rollout` — the nemesis walking nodes one release at a time, forward and back, under the usual partitions and crashes — asserting that no node is ever sent a form of a message its build cannot read (compatibility §4). The frame vocabulary's postcard discriminants are pinned too, against the insertion that would silently shift every frame after it.

**What is missing** is that the sweep's revision-varying behavior is the workload's own. Every production window in `crates/` is a single revision wide; the only multi-revision windows in the tree are inside tests. So the sweep varies a synthetic `Form` on its own message rather than a tree format: the gate is shown usable and a build ignoring it is caught, but no real format is exercised across a rollout, and no granary invariant or linearizability check is asserted across the transition.

**Decided 2026-08-07: build the machinery, not the revision — and only the machinery that costs nothing to hold.** A working `actor.wire` revision 2 was built end to end and pulled back: a gated frame appended to `Frame`, a `v2.bin` corpus fixture, the cluster-wide minimum of §1.4 folded from it, and both sweeps carrying the property over the real format. A second pass then removed the *seams* it left behind as well — a `Frame::revision` returning a constant, a receive-side refusal that only a contrived test could fire, a `Transport::local_window`, a catalogued invariant that could never trip, and a granary rolling sweep that largely duplicated the restart sweep beside it. Roughly sixty lines of production code across five files, all of it inert, one call of it on the path every inbound frame takes.

The reasoning both times was the same. A revision invented so that something could exercise the machinery is a revision every later build carries under **V5**, for a rollout nobody is performing; and a seam that cannot fire until that revision exists is not insurance, it is maintenance. The knowledge belongs where this tree already puts unfinished work — declared in a spec, where a reader sees its cost and its blast radius — rather than left as scaffolding beside the code. What was kept is the one test that earns its place without a second revision: `frame_discriminants_are_stable`, because `actor.wire`'s golden corpus pins the `Hello` preamble and nothing pins the frames, so an inserted variant is caught by nothing at all.

**What would reopen it:** a format change something actually needs, or a deployment whose upgrades are worth rehearsing against. The build being *possible* is not new evidence; it has been done once, and the second pass is written down here so it is not attempted a third time.

**Next step —** it lands with the first real format change, and the work left at that point is small because the seams are in place. For a wire bump: widen `WIRE` to `Window::new("actor.wire", 1, 2, 1)` in one release and flip to `…, 2, 2)` in a later one (**V4**); append the new variant rather than editing one and extend `frame_discriminants_are_stable` to pin it (`crates/actor-cluster/src/protocol.rs`); teach the frame which revision a reader needs and gate the send on `Transport::peer_version`, remembering that `None` means *not yet known*, never *anything goes*; give a simulated node a way to answer with its *own* window rather than the build's constant, or the sweeps cannot roll one binary through releases; check in `crates/actor-runtime/corpus/actor.wire/v2.bin` beside `v1.bin` and bump the §3 registry row. The `Rollout` vocabulary and the sweeps that drive it need no change. For a *durable* bump the extra piece is a seam that does not exist: a rollout changes what a node sends, where a durable revision changes what is already on disk, so the workload must write records under one revision and read them back under another — a restart onto a widened window, not a nemesis action. Done when a seeded sweep exercises a real format across a version boundary, in either direction.

### 1.2 The Raft log's app payloads refuse by parse failure, not by revision

**Status:** open — the fail-closed half of both landed on 2026-08-07; the boundary that would name what they refused did not, and the cluster-level proof did not either.

Two payloads ride `EntryPayload::App` inside the stamped `actor.raft.log`, whose revision covers the envelope and not them: `ShardMapCommand` (granary §7.6, `serde_json`) and `MembershipCommand` (actor §9.4.3 item 1, a fixed 9-byte tag-plus-node form). **The divergence both used to cause is gone.** Neither decoder ends in `.ok()` at its apply site any more. A node that cannot read a committed shard-map command stops applying the map's log, freezes its allocation at a prefix of it, hands off every shard it leads, stops its proposer loops, and reports why through `ShardMapSource::poisoned` (`crates/granary/src/shardmap.rs`). A node that cannot read a committed membership transition does the same: stops applying, hands the control-plane duties to a peer, keeps gossiping and acknowledging, and reports why through `Membership::failure` (`crates/actor-cluster/src/{membership,system}.rs`). Both owning specs carry the reasoning, including why stopping is safe where skipping was not.

**What is left is a name for each refusal.** A build meeting a payload from a later build stops on a serde error or an unknown tag, which reads exactly like a damaged log. With a boundary it would stop on *"revision 2, and I accept 1"* — the difference between an operator reading a mixed-version rollout and reading corruption.

**Next step —** the shard map first, since stopping costs it more (compatibility §5 says why: a stopped membership can still be told the outcome by gossip, and a stopped shard map cannot). A `granary.shardmap` row in the compatibility §3 registry, a revision ahead of the JSON payload, and a corpus fixture at `crates/granary/corpus/granary.shardmap/v1.bin`; the completeness gate (`crates/compat/tests/golden_corpus.rs`) demands the fixture the moment the row exists, so the three land together. The stamp goes around the *payload* inside `EntryPayload::App`, not around the log entry, which is stamped already. Then `admit` (`crates/granary/src/shardmap.rs`) unstamps before decoding and carries the revision into its refusal — and it must **adopt an unstamped payload as revision 1**, the way every other boundary in the tree adopts its predecessor (compatibility §3), or the first rolling upgrade refuses every command committed before the stamp existed. `actor.membership` is the same shape over `MembershipCommand::encode`/`decode`, with one extra cost to weigh first: that payload is fixed at nine bytes today and a revision widens every membership entry ever written.

Separately, the halting property is proved today only by unit tests beside each decoder, which cover the decision and the stopped flag but not the cluster. That a *cluster* refuses rather than diverges still wants the mixed-version workload the original entry called for: one node on a build that knows a variant and its peer on one that does not, over §1.1's `Rollout` sweeps. Done when a build that meets a payload it cannot read says so by revision, and a seeded sweep shows the cluster halting rather than drifting.

### 1.3 A log's record-schema stamp understates after a bump

**Status:** open — nothing built. Fail-closed, and compaction is a working operator-side workaround, which is why it sits below §1.2.

`wal` writes the caller's record-schema revision into the fixed 16-byte header once, at create (`header()`, `crates/wal/src/lib.rs`). `append` then writes frames at whatever revision its build writes without touching that header, so once a caller's window spans two revisions the stamp understates what the file holds until a compaction restamps it (wal §2.1 rule 5). This is fail-closed — the header claims less than the file contains, so a reader refuses rather than misparses — and compaction is the workaround, which is why it sits below §1.2.

**Next step —** on the first append whose `records.writes()` exceeds the revision recorded in the header, rewrite those two header bytes in place through a second, non-append handle (compatibility §5 names this shape). The ordering is the whole of the work: the header must claim the higher revision, durably, *before* a frame at that revision lands, or a crash between the two leaves exactly the understating file this fixes. Done when a `Wal` created at revision 1, reopened under a window that writes revision 2, and appended to, reports revision 2 in its header with no compaction — and a crash injected between the two writes leaves a file that still opens.

### 1.4 A cluster-wide minimum revision

**Status:** postponed — built once and pulled back on 2026-08-07 (§1.1's decision), because it has no caller until a boundary has a second revision to gate on. Reopens with §1.1.

Each build announces the range it accepts at a boundary (`Window::accepted()`), and `actor.wire` negotiates that per association (compatibility §3.1). Nothing aggregates it across the cluster, so **V4** — do not write a form until every peer can read it — is a policy an operator follows rather than a mechanism the code enforces. It sits below §1.1 because it has no caller until a boundary has a second revision to gate on.

**Next step —** carry each member's announced range in the SWIM gossip digest (`MemberDigest` in `crates/actor-cluster/src/membership.rs`, which already rides `Ping`/`Ack`/`PingReq` in `protocol.rs`), or in a frame of its own if the digest's four riders make a positional layout change too expensive, and expose the cluster-wide minimum as something a caller can gate on. Two hazards, and the second is the one that bites. A node that has not yet heard from a member must read the minimum as *not yet known* and write conservatively, never as *no constraint* — the hazard §3.1 already states for `peer_version`. And **only first-hand evidence can retract**: a node that rolls back runs a build that cannot announce its own retraction, so a belief built from announcements alone stays wrong until something narrows it from the association. Compatibility §3.1's design note is the long form. Done when a behavior can ask the cluster, rather than its own build, whether it may write a form.

## 2. Where the sweeps do not reach

Known gaps between what the simulation sweeps exercise and what the specs mandate (simulation-testing, *Where the sweeps do not yet reach*, which owns all three). Each is a place a bug could live undetected today.

### 2.1 Granary alarms have no continuous sweep

**Status:** open, and the evidence is disputed — a stronger claim about this subsystem was recorded and then reverted with no reason written down (below). Reproduce before building anything.

At-most-once firing is now catalogued as **G21** and verified by scenarios (`alarm.rs`, `alarm_cluster.rs`), but a `ClusterWorkload` asserting it under the continuous nemesis trips `no-silent-loss` on about one seed in ten — *"1 ask(s) still pending at quiescence"*. The alarm driver polls its shard's index every 500 ms for as long as its node lives (`ALARM_DRIVE_INTERVAL`, `crates/granary/src/grainref.rs`), so an alarm-wired granary never reaches ask-quiescence. Nothing is lost — those asks carry the 5 s `DEFAULT_ASK_TIMEOUT` and do resolve — so this is a check meeting a subsystem it was not written for.

**Settle this first.** A commit on this branch, `932ebca`, recorded a stronger claim than the paragraph above: that an alarm-wired granary does not commit *at all* under plain frame loss — no partition, no crash — the grain activating, never committing, being passivated, while the caller hangs to its own deadline, with a controlled differential against plain `granary` on the same seed. It was reverted by `557ad1a` with no reason recorded, and the milder quiescence story replaced it. Its named suspects were demonstrably wrong: both cited asks are bounded by `DEFAULT_ASK_TIMEOUT` (`GrainRef::ask`, `ActorRef::ask`). Whether the *symptom* was explained away or merely dropped is written down nowhere, and the workload that produced it was never committed. Reproduce it before building the sweep — if it is real, the sweep is not the work.

**Next step —** build the `ClusterWorkload` on `granary_with_alarms::<Timer>` over the hoisted fixture in `crates/granary/tests/support/timer.rs`, which `alarm_cluster.rs` and `alarm_index.rs` already drive, and take the fourth way out of the quiescence problem: drop `NoSilentLoss` from `default_invariants()` (`crates/actor-simulation/src/invariant.rs`) exactly as `crates/blob-store/tests/swarm.rs` does in its `invariants()`, writing down the same reasoning. That move is honest only while the workload awaits every op it issues to an outcome, which is what leaves the data path's no-loss covered with the checker gone; if that reads as too weak, the alternatives all change the runner or the driver — exempt background-loop asks from the tally, require in-flight-zero over a sustained window, or give the driver a way to stand down. Done when a seeded sweep asserts **G21** under the continuous nemesis and passes every seed, not nine in ten.

### 2.2 Granary workflows have no sweep at all

**Status:** open, attempted — a workload was built, measured, and not committed. What is missing is a shorter fixture, not more effort against the current one.

What is assertable is not "the effect ran once" — `LaunchGuard` is per-activation and never journaled, so a re-activation legitimately re-launches an unresolved step (granary §7.17) — but that the **memo is write-once**: `complete_step` records only a step that is not already done, so the first committed result wins and every later drive resolves from it. Observing that needs a chain: commit a step, be interrupted, re-launch, then be readable. The seeds that get far enough to observe anything are the calm ones that never re-launch, and about two in twenty-four observe a memo at all. More seeds and a longer settle were both tried and moved nothing.

**Next step —** shorten the chain until one commit suffices. Today's fixture (`crates/granary/tests/workflow.rs`) opens with an ask — `Pipeline` accepts a `Start` message — so a round trip has to succeed before the workflow commits anything; dropping it in favour of activating on first touch is the obvious first cut. Alongside it, give the effect a value that differs on each run (a counter, not a constant), because a constant-valued effect cannot tell an overwritten memo from a preserved one. Then assert write-once against the memo rather than against the effect count. Done when a seeded sweep observes a memo on most seeds and re-launches on some of them — the two conditions that currently never co-occur.

### 2.3 Three crates have no sweep

**Status:** open, and blocked on a decision rather than on effort — what a *fault* even is at an I/O boundary has never been settled, and the code cannot start before it is.

`harness-sandbox`, `harness-gateway`, and `machine-frontdoor` are I/O-boundary crates rather than distributed ones, so the simulator reaches them only indirectly. Each has tests; none has a `ClusterWorkload`.

**Next step —** the decision comes before the code. These crates fail at an edge the simulator does not model — a process boundary, an HTTP boundary, a TCP one — so the first question is what a *fault* even is there and which invariant survives it. Pick one crate and answer that in its own spec's terms before writing a workload; a sweep whose faults the simulator cannot inject asserts nothing while looking like coverage, which is worse than the gap it closes. Done when one of the three has a stated fault model, whether or not a sweep follows.

## 3. Deferred by design

**Status: by design**, for every entry below. Scope calls, not oversights, and not postponements a session can revisit on its own evidence — the difference from a **postponed** item in §1 or §2 is that the owning spec *considered and declined* these, so the move is to change its mind rather than to build what it turned down. **They carry no next step** for that reason, and each is recorded only so a reader does not mistake it for something forgotten. Read the cited section first — it holds the reasoning and the cost that the summary here compresses away.

**Consistency and reads.** Reads are **read-your-leader** (relaxed), so a deposed-but-unfenced minority leader can serve a stale read; writes never fork (granary §7.5, §8). The upgrade is a check-quorum lease on the shard's leader-election group, with follower reads as a separate extension (granary §16). The harness inherits this: a `Tail` is exactly this read, and its linearizable form rides the grain's extension rather than a harness mechanism (harness §10.1, §13).

**Storage scaling.** Lazy hydration is deferred at all three facets and for the same reason each time — an activation materializes the whole artifact rather than the part the next session touches: SQL pages behind a capture VFS, workspace files with ranged sub-records above the 64 MiB tree cap, and disk blocks from checkpoint blobs (granary §16, machine §8). Alongside them: disk overlay dirty tracking to replace the reference content-hash scan, proactive blob re-replication on membership change (deferred in lockstep with the same work for records and snapshots), range-verified blob streaming against the BLAKE3 tree the `BlobId` already roots, and a linear `async` DSL over the workflow facet.

**The machine** (machine §8). Memory-snapshot warm resume, so a migrated machine keeps its running processes instead of rebooting the guest; within-connection SSH migration, which needs that snapshot plus connection-state handoff at the front door; point-in-time restore and forking, which need policy before they need mechanism; richer ingress (port forwarding, HTTP preview, TCP); and per-owner quotas. Credit-based flow control across the actor transport is likewise open. Separately, the cross-node front-door relay is deferred, so each node's door serves only the machines it hosts (`crates/machine-standalone/src/node.rs`).

**The agent** (harness §13). Context compaction — an over-long transcript fails the run explicitly today (`crates/harness/src/model.rs`); durable-alarm integration, where the grain half exists and the harness half does not, so resumption is strictly caller-driven; a scheduler singleton above it; token streaming and push-based run observation; per-call permission gating, the dynamic half of an authorization story whose static half is the tier cap; loop-executing tools beyond the built-in `delegate`; code mode; external trace interop; and cross-session sagas.

**The sandbox** (sandbox §7). No tier accepts inbound connections, so a sandboxed server is reachable only from inside its own environment. Warm pools and per-tier snapshots are the shared upgrade with the machine's memory snapshot above.

**Cluster utilities** (cluster-utilities §7). Cluster sharding by `(entity type, entity id)` over §2's placement; distributed pub/sub over per-node topic mediators; and a leader-anchored singleton that trades the §4 convergence caveat for a quorum-gated activation. The singleton is not a mutual-exclusion primitive until that lands.

**`wal`** (wal §8). Group commit across handles, and only if a caller needs it. The rest of that section is non-goals, not deferrals.

## 4. Finished but unused

**Status: done**, and listed only because "done" is invisible on a page that deletes what lands. This one is the exception to that rule: a complete crate nothing depends on reads like an oversight from every direction except this note.

**`blob-store` has no in-tree consumer.** The crate is complete against its spec (B1–B7), carries its own cluster sweep, and nothing in the workspace depends on it — the docs index says so, the workspace manifest says so beside the dependency itself, and no crate names it. It is the **cold** half of the hot/cold split: granary's grain-colocated blobs, not this, serve the live path (granary §7.10). Nothing to do here; it is recorded so a reader does not take a change to it as load-bearing.
